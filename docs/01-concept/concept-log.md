## 過程記錄

### 關於文件與紀錄方式

- 決定以「階段」而非日期劃分文件。理由：commit 本身已帶日期，檔名再寫日期是重複；外部讀者關心的是進行到哪一步，而非哪一天。
- 決定不預先定義全部階段名稱。理由：階段的形狀要走完才看得清，先定死名稱會為了遷就名稱而扭曲內容。只定眼前這個階段，並為它寫明結束條件。
- 決定一個階段一份長文件，逐步向下增補，而非一個議題一份。理由：要呈現的是演化過程，分拆成獨立議題會失去這條線。
- 暫不設 README。等 repo 內開始有 code 等其他內容時再補。

### 關於引擎選擇（早前已決定，此處保留脈絡）

先前曾在 UE5、Unity、Godot 之間比較。最終選 Godot：2D 支援直接、體積小、開箱即用、MIT 授權無 royalty。UE5 雖然最熟悉，但對 2D 小型 project 是過度配置。

## 設計柱（Pillars）

三條柱由已確認前提中抽出，並非另外新增。它們互相扣連，抽走任何一條，其餘兩條也會塌。

1. **非操作導向。** 抽走它，遊戲就必須有操作，而所有事前配置的意義都會被即時操作蓋過，「配置完看它跑」整個形態不成立。
2. **變化來自 gameplay / system，而非新增內容。** 抽走它，replayability 就回到內容驅動，即是要靠不斷產出新內容維持，一人開發走不完這條路。
3. **高配搭性、系統互相組合。** 抽走它，就沒有再開一局的理由，也沒有第二條柱所需的變化來源。

三者的因果是：因為不要操作，所以樂趣要來自配置；因為不靠新增內容，所以變化要來自組合；因為要有組合，所以系統之間要有互動。

至於「2D」「Godot」「盡量重用 assets」等，抽走之後遊戲仍然成立，它們是限制，不是柱。

### 測試方法

判斷一件事是柱還是 feature，方法是抽走它，看整個東西還站不站得住。站得住的是 feature，站不住的才是柱。

此方法由《金庸群俠傳 2／3》這個例子驗證出來：抽走金庸這個題材後，該遊戲並非少了一部分，而是整座塌下來——因為它的武功、事件、分支、NPC 全部由原著提供。narrative 對它而言不是其中一條柱，而是主柱。

這個測試比「寫三至五條 pillar」實用，因為它會即時篩走那些聽起來好聽但其實無關痛癢的所謂 pillar。

## 三個既有構想的現況

三個構想來自先前與 ChatGPT 的討論，性質是參考資料，不是可直接套用的方案。即使採用，也會再改。

### A — 魔塔 / roguelite

定位：**後備。** 想不到其他方向時的 fallback。選它的理由是複雜度高，但技術可行性夠高。

三條柱測試：全部通過。抽走 narrative 不會塌，因為它的獎勵是「這組配置跑出什麼結果」。

複雜度集中在架構與平衡：效果如何表達、何時計算、如何疊加；組合一多就要調平衡，而平衡要靠反覆試玩才調得準。

需注意：A 原本掛著的一批元素（職業、多重職業、獨立技能樹、party、quest、多結局、achievement）當時屬 brainstorm inventory，未經柱測試。逐項測過之後，剩下的可能比預期少。

### B — 養成遊戲

定位：**不用 AI 也做得到，但它多數要故事，而故事與本次方向衝突。**

三條柱測試：第一條通過（每日按 UI 選行動）。第二條不通過——再開一局的理由是「還有劇情沒見過」，屬內容驅動。第三條部分通過——數值與事件有互動，但主要是條件觸發，不是組合。

補充分析：B 拿走故事後，loop 仍然行得到，但要有另一樣東西頂上玩下去的理由。可能的方向有二：一是目標本身夠有張力（明確結算標準加時限，玩是為了達標而非為了看劇情）；二是行動之間有組合（行動不再各自獨立加數，而是互相影響、互相排擠、某些組合觸發第三種效果）。若照第二個方向改，B 就不再是內容驅動，反而向三條柱靠近——但那時它已經不是傳統養成遊戲了。

### C — AI 作為 engine 原生能力

定位：**有難度，暫時不搞。**

它不是一隻遊戲，是加在遊戲之上的一層，而它寄生在 B 之上。B 不行，C 就沒有載體。

技術層面：格式可靠性已有解（schema-constrained decoding）；但格式對不等於內容對，內容層需要另建 rule-based 驗證層、受控詞彙表、fallback 機制。真正的難處是這一層沒有做得完的一天——要玩夠多次才知道 AI 何時開始偏離設定，而每次收緊規則又要重測。屬開放式研究，不是一個可完成的 feature。

另外，C 學到的是 LLM 整合，不是 Godot，與本專案的技術目標不對口。

## 已排除的方向

### 《金庸群俠傳 2／3》（Flash 版）

排除。兩個理由：

1. 金庸 IP 有版權，題材無法直接使用。
2. 更關鍵的是，它以 narrative 作主柱。抽走題材不是換皮，而是要從零建立一個世界與一整套劇情，那本身是另一個 project。而且它的重玩性來自「還有劇情沒見過」，與本次「內容變化來自 system」的方向相反。

保留脈絡：其結構中真正與金庸掛鈎的只有「代入原著角色的遭遇」一項。學習點取捨、熟練度升級、悟性影響修煉效率、分支劇情、隊友收集等，都是通用結構。

### Greed Island 式的整體結構

排除作為主體。

其表面結構（固定格數收集表、萬物可卡化、指定格與自由格兩層空間）三條柱都通過，但支撐這個結構的是內容——100 格每一格背後都是一段獨立設計的獲取條件（puzzle、對戰、NPC 交易、事件鏈）。抽走 event 與 narrative，binder 就是一個沒有東西可填的空框。

替代做法是用 puzzle / mini game 取代 event，但那樣 scope 是線性增長：多做一格就要多做一次完整設計，沒有任何系統性複用，與第二條柱正好相反。

## 備案

### 卡片制（未決定）

指卡作為載體的一套機制，不是要做卡牌遊戲。可用的結構有四項：

- 固定格數的收集表本身就是進度顯示與目標，玩家永遠知道自己差多遠，不需要旁白或劇情交代。
- 萬物可卡化，且變回實物後不可逆。即是「用掉」與「收藏」互斥——手上這張，是留著填格，還是拿出來用。這是一個持續的取捨，且完全不依賴數值。
- 兩層 slot：指定格有位置對應，自由格有限量。背包本身成為一個資源管理問題，而不是一份無限清單。
- 收集本身有依賴鏈：有些要先取得其他項目才拿得到，因此需要規劃次序。

這四項是結構，與「每一格背後要手工設計獲取條件」是兩回事——後者才是內容負擔。

## 不成立的篩選條件

記錄於此是為了避免日後再用它們去收窄方向。

### 「一人開發」與「asset 成本」

不是有效的篩選條件。

- asset 已經是既定前提（主要使用現成 assets），不是待解問題。
- 有 solo dev 的實例顯示，鎖定一套現成 spritesheet 反而幫忙收 scope、逼人用手上的東西發揮，兩星期就能把 prototype 推得很遠。
- 「一人開發」是事實，不是限制。限制會篩走選項，事實只決定做法。加上時間無限期，它在本專案的影響本來就小。

**但：** asset 可以作為一個**主動採用的收窄方法**——先鎖定一套 assets，反過來用它收窄設計空間。這是手段而非約束，目前未決定是否採用。

### style / theme 類 filter

判斷為不走這條路。題材、美術風格、視角、基調這類 filter 可以套在幾乎任何機制之上，彼此沒有必然關係，因此收窄力不足，反而多開一條要想的線，增加負擔多於減少選項。

## 決定：先做簡易魔塔，跑得起再加機制

不再是「後備」。A 的核心（魔塔骨架）成為現行起步方向，且明確定下開發次序：先把一個能完整跑起的簡易魔塔做出來，之後才在上面逐步加入新機制。不是邊做骨架邊加機制。

A 原本掛著的一批延伸元素（職業、多重職業、獨立技能樹、party、quest、多結局、achievement）不在簡易版範圍內，留待骨架跑起之後，逐項用「抽走會否塌」測試，再決定加或不加。

### 簡易魔塔的範圍：已定

魔塔類型的傳統元素（技術支援整理，已經 Paul 確認）：除特殊道具外全部要做齊。

- 戰鬥：固定數值計算，非隨機。傷害次數 = 敵人生命值 ÷（玩家攻擊力 − 敵人防禦力）；玩家受到的傷害 = 傷害次數 ×（敵人攻擊力 − 玩家防禦力）。戰鬥前可預先算出結果。
- 核心資源：HP、ATK、DEF、金幣、經驗。
- 鑰匙：黃／藍／紅三色，稀有度遞增，開對應顏色的門，一次性使用。
- 血瓶：紅／藍兩色，藍色恢復量為紅色的四倍，恢復量依塔內所處區域決定。
- 寶石：紅寶石加攻擊、藍寶石加防禦，永久生效。
- 祭壇：三選一提升生命／攻擊／防禦。
- 怪物手冊：查看怪物數值與特殊屬性。解鎖方式：由一件獨立的 unlock 道具解鎖——拿到即永久解鎖此功能，屬一次性 unlock，非消耗品，與下方「特殊道具」不同類別。
- 地圖：固定格子構成的樓層，可依區域分段、難度遞增。

不含在此範圍（排除為「特殊道具」，指消耗品／工具類）：十字架、藏寶圖、超級炸彈、傳送器等。是否日後加入未定。

技術對口：技術目標原定涵蓋 UI、Scene Management、Save/Load、Data Persistence 等 Godot 常見 workflow，此類型的實作通常會用到 TileMap（grid 與樓層）。傳統魔塔的固定數值戰鬥公式，天然符合「戰前可預判、非即時操作」的方向，故戰鬥結算「是否需要額外的可配置中介層」此問題視為已由此公式回答：核心戰鬥本身即為預先可計算的公式，不是寫死的即時判定。

打不過的敵人（玩家 ATK ≤ 敵人 DEF）系統直接阻止攻擊（不允許出手，非扣零血），此為設計核心而非邊界情況需迴避——玩家判斷哪些怪打得過、哪些要繞路，本身是玩法的一部分。

## 素材方向：已定

放棄「不用 RPG Maker 官方素材、要可商用」此一原有限制，理由是專案方向已改為不走商業化、走開源。

### 已有素材：自製 SWF

一個由使用者自行製作的 Flash（SWF，Flash Player 6）魔塔素材檔，內含 155 張點陣圖，其中 133 張為 32x32。內容涵蓋敵人（多組換色分級，如史萊姆／骷髏／獸人）、道具與 UI（鑰匙、寶石、藥水、劍、盾、書、炸彈）、地形（牆、地板、樓梯、柱、閘），另有 96x96 與 390x400 大圖各數張未拆解內容。Symbol 命名顯示原作採「Icon + 編號」統一索引方式，並有七個對應魔塔經典道具技能的 button（冰凍、萬能鑰匙、地震、跳躍、挖礦、聖光、炸彈）。

因為是自製，此檔案無第三方授權問題，不需列入 credits 清單。tile size 已由此檔案確定為 32x32。

### 素材來源脈絡：魔塔類型的公共素材生態

經查證，這套風格的 32x32 魔塔素材在中文魔塔社群中屬於長期公開流通的共用資源，非單一來源獨佔：

- WDMOTA（百度貼吧魔塔愛好者建立的網站）設有專門的「素材專區」，站方聲明下載不收費、不含商業廣告。
- scratch5.com 有專頁提供「2D像素風格魔塔冒險遊戲素材」下載，說明文字為「非常經典」。
- h5mota.com（HTML5魔塔廣場）以自研引擎與編輯器為基礎，收錄超過 2000 座玩家自製的塔，編輯器本身支援使用者直接拖入素材圖片自動註冊，反映此類素材在該社群作為共用底材的使用方式。
- 連 RPG Maker 平台上的商業化重製版本（魔塔重製版，RPG Maker MZ）也公開說明其設計架構參考自三原塔（原始魔塔／胖老鼠魔塔／新新魔塔），顯示這個類型本身是建立在長期互相參考的傳統之上。

未見任何一方對此套視覺主張專屬版權或標註來源歸屬。

### 素材處理原則（三級）

1. 付費素材、已購買的商業內容：版權明確，依其條款處理。
2. 免費但註明授權條款的素材：依該授權條款處理。
3. 無授權聲明、年代久遠、於相關社群通行流傳的素材：使用時附上出處說明（credit），視為已盡合理注意。

目前的自製 SWF 屬於第一類的例外（自己擁有），若後續另外取用魔塔社群其他素材則屬第三類，依此原則 credit 處理。

### 其他備選路徑（未定，並列）

- 尋找規格相符（32x32、top-down、fantasy dungeon）的 CC0 素材作補充或替代。
- 以現有素材為風格參考，用 AI 生成新素材，再視生成工具本身的授權條款決定商用可行性。

三條路徑（自製 SWF、社群共用素材、AI 生成）不互斥，可視開發階段搭配使用。

## 基準版本：以手上的 SWF 版本為準

做法定為 **reuse + renew**：

- **Reuse**：此 SWF 版本的規則、系統結構、數值框架、素材，全部作為基底沿用，不重新發明。
- **Renew**：不是做 pixel-perfect 移植，而是在這個基底上做自己的版本。改什麼、加什麼、換什麼，逐項另行決定。
- **輸出形態**：以 Godot 匯出成 exe（桌面執行檔），非 web／Flash。

規則、數值結構、系統範圍全部以手上這個 SWF 版本為準，不採用其他魔塔版本的做法。以下為直接反編譯該 SWF 的 ActionScript 得出的事實，非推測。

### 存檔

- 五個存檔位（Load0 至 Load4）。
- 儲存的是 snapshot：玩家狀態（SavPlayer）與各層物件狀態（SavObj_array），即單一時間點的完整狀態。
- 沒有復盤／退步／回溯系統，程式碼中無任何 undo 或 history 相關函式。
- 原版以 Flash SharedObject 實作（存檔名 czlmt200401）；在 Godot 需另選對應做法。
- 快捷鍵：S 存檔、L 讀檔、R 重置。

### 樓層

- 只有 TotalFloorNum、FloorNo、MaxFloorNo，沒有「區域／分區」概念。
- 血瓶恢復量、寶石加成等數值屬於各個 icon 自身的屬性（Obj_array 按 floor 儲存 icon），不是由所在區域推算出來。此點與部分其他魔塔版本（按區域決定數值）不同，本專案以 SWF 版本為準。

### 玩家屬性

Life、Offense、Defense、Money、Weapon、Shield、KeyYellow、KeyBlue、KeyRed、MagicDamage、Multiple、Speed、BuyNum。

沒有經驗值系統：屬性提升透過商店以 Money 購買（ShopLife／ShopOffense／ShopDefense 三選一）。此即先前記錄中「祭壇三選一」的對應實作。

### 道具（Cowry）

Cross、Luck、Dragon、Help、Note、FlyUp、FlyDown、Ice、Holy、KeyMagic、Pick、Quake、Bomb、JumpUp、JumpDown、Jump。

兩種類型，程式碼上明確分開：

- Unlock 型：Note（怪物手冊）、Help 等，以 enabled 屬性控制，拿到後永久開通。
- 消耗／次數型：如 Jump，有數量顯示（CowryJumpNum_txt）。

### 戰鬥

- 計算函式：calcDamage、calcMagicDamage。
- 魔法攻擊分四個方向（MagicUp／MagicDown／MagicLeft／MagicRight）。
- 打不過的敵人顯示「!!!」。

### 產出

- `tileset_32_index.json`：對照表。每個 tile 的 atlas 座標對應原 SWF 內的 character ID，供日後對照原始地圖資料（Obj_array 儲存的是 icon 編號）。

### 動畫：原作有，決定跟原作做

反編譯確認原作 142 個 sprite 中有 130 個為多幀，多數為兩幀循環——即先前抽出的 133 張圖中，大量看似重複的圖其實是同一個物件的兩個動畫幀，不是重複素材。

分佈：

- 39 個 Icon 為兩幀循環（多為敵人）。
- 55 個 Icon 為靜態單幀（道具、地形、門、樓梯等）。
- 6 個 Icon 為三至四幀（Icon210、Icon51、Icon105、Icon104、Icon103、Smallkey）。
- 16 個 Icon 不使用 bitmap，為純向量繪製，在提取的圖檔中無對應項。
- 20 張圖屬於 Player 與 NPC（玩家四方向行走各兩幀、白袍老人、紅袍商人、兩隻大型敵人的 32x32 版本），不經 Icon 系統擺放，故不在 Icon 對應表內。

決定：跟原作做，保留動畫。實作上 Godot 可用 AnimatedSprite2D，或 TileSet atlas 內建的 animated tile 功能。

註：SWF 中 character 40、80、110、256 為 DefineShape（向量形狀，非點陣圖），故不在提取的圖檔內。

### 音效：已提取

### Godot 2D 相關限制（查證所得）

- 預設 texture filter 為 linear，會令 pixel art 模糊。需在 Project Settings → Rendering → Textures 將 Default Texture Filter 設為 Nearest。
- Godot 4 使用 TileMapLayer node（非舊版 TileMap），每個 node 代表一層。
- TileSet 建議使用單張 tilesheet（atlas）而非一圖一 tile，官方文件指出前者可用性較佳。
- TileSet atlas 有 Use Texture Padding 選項，會自動在每個 tile 周圍加 1 pixel 透明邊防止接縫，官方建議保持開啟。
- 匯入 atlas 後，Godot 會詢問是否自動由非透明區域生成 tiles，可一次過建立全部 tile。
